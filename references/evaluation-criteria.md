# 评估标准参考

## 功能性评估（40%）

### 核心功能（必须）
- [ ] 主要功能按规格实现
- [ ] 功能流程完整（输入 → 处理 → 输出）
- [ ] 数据正确性（计算、存储、读取）

### 边界情况（重要）
- [ ] 空输入/空值处理
- [ ] 超长内容处理
- [ ] 特殊字符处理
- [ ] 并发/重复操作处理

### 错误处理（重要）
- [ ] 网络失败处理
- [ ] 无效输入提示
- [ ] 操作失败恢复
- [ ] 错误信息友好

### 数据持久化（如需要）
- [ ] 数据正确保存
- [ ] 数据正确读取
- [ ] 数据格式兼容
- [ ] 备份/恢复机制

**评分标准**：
- 10分：所有功能完美实现，边界情况处理完善
- 8-9分：核心功能实现，少量边界情况未处理
- 6-7分：核心功能基本实现，有明显边界问题
- <6分：核心功能有缺陷或缺失

---

## 代码质量评估（30%）

### 可读性
- [ ] 命名清晰（变量、函数、文件）
- [ ] 有必要的注释
- [ ] 代码格式统一
- [ ] 逻辑清晰易懂

### 结构
- [ ] 模块化设计
- [ ] 职责分离
- [ ] 无重复代码（DRY）
- [ ] 依赖关系合理

### 最佳实践
- [ ] 符合语言/框架规范
- [ ] 使用标准库/常用库
- [ ] 安全实践（防注入、防 XSS 等）
- [ ] 性能考虑

### 可维护性
- [ ] 易于修改
- [ ] 易于扩展
- [ ] 易于测试
- [ ] 配置与代码分离

**评分标准**：
- 10分：代码优雅，是最佳实践的典范
- 8-9分：代码良好，符合规范
- 6-7分：代码可用，有改进空间
- <6分：代码混乱，难以维护

---

## 用户体验评估（20%）

### 界面美观
- [ ] 布局合理
- [ ] 配色协调
- [ ] 字体清晰
- [ ] 间距舒适

### 交互流畅
- [ ] 响应及时（< 200ms）
- [ ] 操作反馈明确
- [ ] 状态可见
- [ ] 过渡自然

### 易于理解
- [ ] 新手能看懂
- [ ] 操作指引清晰
- [ ] 术语易懂
- [ ] 帮助文档完整

### 错误友好
- [ ] 错误提示明确
- [ ] 提供解决方案
- [ ] 不丢失用户数据
- [ ] 容易恢复

**评分标准**：
- 10分：体验出色，超出预期
- 8-9分：体验良好，用户满意
- 6-7分：体验一般，可用但不够流畅
- <6分：体验差，用户困惑或沮丧

## 评估技巧

### 对于 Evaluator 代理

1. **先测试，后评分**
   - 实际运行代码
   - 尝试各种输入
   - 观察边界情况

2. **对照 Sprint 合约**
   - 检查合约中定义的功能
   - 验证合约中的测试用例
   - 确认完成标准

3. **给出具体反馈**
   - 不只是"不好"，要说明"哪里不好"
   - 提供改进建议
   - 举例说明期望的行为

4. **保持一致性**
   - 使用相同的评分标准
   - 参考之前的评估报告
   - 避免评分漂移

### 对于开发小白用户

1. **不懂技术也能评估**
   - 功能是否工作？（功能性）
   - 看起来舒服吗？（用户体验）
   - 能看懂怎么用吗？（用户体验）

2. **给出具体反馈**
   - "这个按钮太小了" ✓
   - "不好看" ✗（太模糊）

3. **接受渐进改进**
   - 第一轮：能用就行
   - 第二轮：好用
   - 第三轮：好看

4. **及时喊停**
   - 如果已经满足需求，可以说"够了，继续下一个"
   - 避免过度优化
